# Dispatch AI: fresh native rebuild

## Product goal

Dispatch is a local-first native workspace where a person gives a team of AI agents a task. Agents make a visible plan, exchange structured handoffs through a shared run timeline, execute independent work in parallel, produce linked deliverables, and run automatic code or visual review before asking the person to accept changes.

This rebuild lives in `native/`. It uses React Native Windows and native Windows controls. It does not import, call, embed, or copy source from Dispatch AI v1. The #14 logo is copied only as a static visual asset.

## Core experience

1. **Dispatch**: describe an outcome, attach project context, select or create a team, choose review gates, and start a run.
2. **Plan**: coordinator proposes typed work items and dependencies. The user can edit/approve the plan before execution.
3. **Coordinate**: agents publish handoffs, questions, findings, progress, and artifact links to an append-only run event stream. Messages can target a named teammate or the whole team; each agent receives team messages, its own history, and messages addressed to it. Independent steps execute concurrently; dependent work becomes ready after its prerequisites pass.
4. **Build**: code, image, and file outputs are stored as run artifacts. Workspace writes and external actions use explicit permission checks and approval gates.
5. **Review**: code review examines the structured file proposal; image review examines the actual rendered asset for requested content, composition, legibility, and visible defects. Findings link to the work item and can return code or image work to its agent for up to two automatic revisions before asking the person to decide. Static checks and test/build evidence are still planned.
6. **Accept**: the user inspects changes and review evidence, then applies or exports deliverables.

## Fresh architecture

- `App.tsx`, `src/`, and `windows/`: native React UI and Windows host.
- `src/orchestration/`: provider-independent run, work-item, team, event, and artifact contracts. `Coordinator` provides dependency-aware concurrent work waves and injected review and approval gates. `model-runner.ts` adds provider-backed planning, parallel agent work, shared handoffs, model-based code-proposal review, and fail-closed image gates.
- `src/persistence/runStore.ts`: local event log and up to 30 resumable run snapshots; team preferences, custom agents, per-agent model IDs and avatar choices, provider profile, and selected project folder are stored separately from secrets. Each run snapshots its full agent profiles so resuming preserves the team and avatars that planned the work.
- Teams screen: users can create and switch among named teams assembled from existing agent profiles. The Hierarchy subtab groups members by rank and edits rank and per-agent project tool permissions, with an explanation of delegated code approval. Team chat shows run messages for the selected team with all, handoff, and review filters; its composer routes a task into Dispatch for plan approval. Advanced settings groups provider, project folder, and automatic review policy.
- Workflows: reusable task briefs can target a saved team and reopen in Dispatch for the existing plan-approval checkpoint. Team playbooks and user-approved agent memory are injected as constrained guidance in planning/execution. Optional debate asks up to three teammates to critique the draft plan and logs their notes in the run.
- Plugins: a local built-in catalog gates the project workspace tools, image generation, code review, and visual review in the execution path. Individual workspace permissions remain separately enforced. Arbitrary third-party code loading is not enabled.
- Design Studio: dedicated workspace with six design starting points, nine selectable design skills, a draggable canvas for reference notes and text-only 3D prompt recipes, exact change/keep brief fields, output format selection, active team context, and accessible move controls. Sending the brief loads all canvas positions, recipe text, skills, and constraints into Dispatch for plan review. After an approved run completes, Dispatch returns to Design Studio and the newest finished image or code proposal is shown in the live output panel. The prompt recipe library does not generate 3D meshes or image assets by itself.
- Task board: the board summarizes work items across saved runs, including owners, dependencies, and current statuses. Run conversations retain workspace tool audit messages and revision proposals. After a restart, runs are recovered from their last saved snapshot: a run that was running or reviewing is marked cancelled with its interrupted items cancelled and a Dispatch note appended (`recoverInterruptedRun` in `src/persistence/runStore.ts`); `replayRun` in `src/orchestration/replay.ts` can rebuild run state from the event log but has no production callers. Side-by-side run comparison is implemented: two saved runs can be compared on status, ordering, work-item statuses, changed files, artifacts, and review findings, and every difference is labelled in words rather than by colour alone. Optional approval checkpoints can pause between dependency waves; Advanced settings can also leave senior-reviewer-approved changes for the user to apply manually.
- `src/persistence/workspaceProject.ts` plus the new `DispatchWorkspace` Windows module: native folder selection, bounded directory listing, UTF-8 text previews, and bounded text grep. Each agent's read, grep, new-file write, and exact-match edit permission is individually configurable and defaults off. Tool requests are checked at execution time and scoped to the selected project. File changes are staged and shown with before/after contents. A qualified peer can approve and apply code changes when it has both code and review capabilities, is rank 4 or 5, and outranks the author; otherwise normal review and human approval gates apply. The native writer is project-root scoped, UTF-8 and size bounded, rejects path traversal and symlink targets, requires explicit create-only semantics for new files, and checks that the original file has not changed before replacing it.
- Image work can call an explicitly configured OpenAI-compatible `/images/generations` model. Returned PNG data is size/signature checked and saved under the app's `%LOCALAPPDATA%` artifact folder; the run and artifact gallery keep its URI, not its base64 payload. A separate vision-capable chat model receives the actual generated pixels for review; unsupported generation/review fails closed to a human gate.
- `windows/DispatchNative/DispatchVault.*`: a new Windows-native module stores provider credentials in Windows Credential Manager. `src/providers/openai-compatible.ts` sends authenticated requests to an OpenAI-compatible API, and the React Native settings screen saves the endpoint/model locally while leaving the secret out of app storage.
- Planned `service/`: new local orchestration service, durable SQLite event/artifact storage, permission broker, and native bridge. This is a new implementation; it must never import v1 modules.
- `assets/`: only static brand artwork needed by this app.

Provider keys belong in Windows Credential Manager; non-secret endpoint and model settings use local key-value storage. Agent tools default to deny and receive only scoped project access. File changes stay staged for the user unless a qualified senior code reviewer approves and applies them. Shell execution and network actions are not implemented. Run events retain tool audit messages, review findings, and artifact/change payloads for reproducibility; artifact hashes are not recorded.

## Delivery sequence

1. Native shell, responsive workspace, persistent teams/review settings, secure provider connection, coordinated text runs, and interrupted-run recovery are implemented; launch-time recovery still needs native runtime validation.
2. Read-only project selection and task context are implemented; local service bridge and durable artifact-capable execution state remain in progress.
3. Plan checkpoint is implemented: users can inspect the saved plan, edit step titles, and explicitly approve before work begins. Cancellation stops planner, agent, and review requests while preserving completed work. Relaunch recovers interrupted runs; people can resume cancelled/failed work or ask a human-gated item to revise from findings. Bounded automatic review-driven revisions are implemented for code and generated images. Per-role model IDs route planner, builder, and reviewer calls through the configured endpoint. Users can define custom agents with instructions and capabilities, and choose from 199 logo-pack avatars; run snapshots preserve these profiles. Custom providers per agent, editing plan assignments/dependencies, and deeper run recovery remain.
4. Per-agent read, grep, new-file write, and exact-edit controls are implemented. Rank-qualified peer code approval and apply are implemented. Line-level diff preview is implemented as a pure helper plus a per-line +/- view. Static checks, test/build evidence, and export remain unfinished.
5. Model-based code proposal review and rendered-image review are implemented as provider-backed checks. Failed code and image checks can trigger up to two agent revisions. Per-file code proposal preview and explicit apply are implemented in the native bridge. Token accounting is implemented: every planner, builder, and reviewer call is recorded to a dedicated local ledger and shown on a Usage screen, split into exact and estimated totals that are never added together. The provider model list is refreshable and shows its own staleness, but it only ever offers suggestions and can never invalidate a model id the person already saved. Static checks, test/build evidence, and export remain unfinished.
6. Windows packaging, signing, update flow, and end-to-end visual/accessibility review on a machine with the Windows native build toolchain.

## Honest current state

The native app can connect to one OpenAI-compatible provider, choose built-in or custom agent roles, assign optional model IDs, and choose avatars from the 199-mark gallery. Agent instructions, capabilities, model IDs, avatar choices, per-agent project tool permissions, and ranks are stored locally; planned runs snapshot agent profiles. The app can generate a plan, wait for the user to inspect/edit step titles and explicitly approve it, then execute team tasks. Provider credentials remain separate. Users can cancel planning, agent, or review requests; completed work stays in the saved run. Relaunch recovers saved runs that were active at shutdown, and the person can resume unfinished work or request another revision from review findings. Agents can route handoffs to teammates; code agents can produce structured file proposals from explicitly attached context and permission-checked workspace tools. Changes are shown with before/after contents. Failed code and generated-image reviews can return bounded feedback for up to two revisions. A code reviewer with code and review capabilities, rank 4 or 5, and a rank above the author can approve and apply the proposal; absent that, the human approval path remains. New files are create-only, existing files use a stale-content check, and the Windows native writer remains unverified until build/runtime validation. Image generation and vision review remain provider-gated. Shell execution, static checks, and export remain unfinished. The orchestration core has headless jest coverage (`__tests__/orchestration.test.ts`). A Debug x64 build plus msix completed on this machine on 2026-10-15 against SDK 10.0.26100.0; launched-app runtime validation of the native writer is still outstanding. Token usage is exact only where the provider reports it; otherwise the app shows length-based estimates, labelled as such and rounded, with no combined total. It has not been verified against any specific provider. The provider model list is a suggestion cache: deleting it, or pointing the provider at one that returns an empty listing, leaves every saved model id loadable and sendable.
